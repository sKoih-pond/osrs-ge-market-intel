## 3. Sources and tables

### 3.1 The Kaggle dump `antonygarand/osrs-ge-5m`, version 1

| Fact | Value | Source |
|---|---|---|
| Files | 70: 68 monthly Parquet files (`prices_5m/year=YYYY/month=MM/data.parquet`, 44.7 to 92.4 MB), `items.parquet`, `README.md` | Kaggle file listing, 21 Oct 2026 |
| Bytes | 4,802,290,041 | same |
| Rows | 876,754,705 item-buckets, 4,539 items | dump README |
| Range | 8 March 2021 07:35 UTC to the bucket starting 17 October 2026 13:10 UTC | assessment |
| Columns | `itemId`, `timestamp`, `avgLowPrice`, `avgHighPrice`, `lowPriceVolume`, `highPriceVolume` (Wiki field names) | dump README |
| Licence | CC BY-NC-SA 3.0, the Wiki's own terms | dump README |

Rules, as built in `ge_intel.kaggle` and `ge_intel.history`:

- **Pin per file.** `src/ge_intel/sources/kaggle_osrs_ge_5m_v1.json` pins every file's size from the listing. The README's SHA-256 is pinned already (`845e67bc…`, downloaded 21 October). The other 69 hashes are recorded by the first verified download and then committed; after that a file that differs is refused, and a file that fails its pin is never silently replaced. A version 2 would be a new source, pinned and checked again.
- **Download.** One file at a time, 5 seconds between files, to `<file>.part`, verified (size, Parquet magic, SHA-256), then renamed, so a file under its real name is always verified. Resumable. A zipped response is unwrapped and checked.
- **`timestamp` × 300.** The column is a bucket number, not the epoch seconds the README says. The conversion multiplies and then checks that every row falls inside its file's month; a file of true epoch seconds fails loudly (tested).
- **Types unified by name.** Price widths differ by month (int32, int64 or double; the two most recent months are always double), volumes int32 or int64. Reads use `union_by_name = true` and cast every column (prices DOUBLE, volumes BIGINT, item INTEGER). The hive `month` key, which reads as text in some files and a number in others, is ignored; the month comes from the timestamp.
- **Shape checks fail loudly:** rows outside the file's month or after `LIVE_START`, non-positive item ids, null or negative volumes, negative prices, rows with neither side traded, duplicate (item, bucket).
- **Provenance per row:** `source` is `kaggle:antonygarand/osrs-ge-5m@v1` or `wiki_api` (hourly rows built from both say `mixed`); 5-minute rows also carry `raw_sha256` (the dump file's hash, or the API response's).
- **Regime per row:** `regime_id` from the regimes seed (ADR-0006), generated into SQL, never hard-coded. A row outside every measurement regime stops the build.
- **Not used:** `items.parquet` (it lists untradeable items and has no missing buy limits, so it is not the GE mapping; buy limits come from `/mapping` snapshots, M1).

## 4. The two design traps

### 4.1 The gap-finder (ADR-0018, decisions 1 and 2)

**Trap:** `tasks.interval_for` (cadence `gap-fill`) starts at the first bucket in `silver/wiki_5m_buckets`. History in that manifest would make about 590,000 buckets "expected" and every hourly run would fetch years of buckets, 96 at a time, unattended.

**Answer, both halves:**
1. **History never enters the live manifest.** It lives in `history/`, which only the history job writes; `history.write` refuses any other table, and tests check that no registry task or weekly maintenance step touches `history/`.
2. **The scheduler looks back 7 days at most** (`tasks.LIVE_GAP_WINDOW`). Worst case 2,016 buckets, about 11 hours of catch-up at 96 a run and two runs an hour. An older live gap is a backfill a person starts (`ge-intel run ingest_5m --start --end`, not clamped; runbook).

**Test:** `tests/test_tasks.py` puts the dump's first bucket (8 March 2021) into the live manifest and checks that the interval starts exactly 7 days back, that only 2,016 buckets count as missing, and that a run asks the Wiki for 96 buckets, all inside the window.

### 4.2 The seam (ADR-0018, decision 3)

**Gap:** from the bucket after 17 October 13:10 to 18 October 23:00: **405 buckets** (33 hours 45 minutes).

**Answer:** `ge-intel history fill` fetches every bucket between the dump's first bucket and `LIVE_START` that the dump does not hold and no earlier fill fetched, **newest first**, so the seam comes first, then the dump's own gaps (the assessment's sample found 6 in October 2026 and 57 in March 2021). **Measured by the first full build** (runner, 21 October 2026): 3,391 buckets missing, the 405 seam buckets plus **2,986 gaps inside the dump**, so the fill is 3,391 requests, about 57 minutes at 1 a second. That is just above the 2,952 unexplained buckets A1 allows, so an empty API answer (a confirmed outage) for some of them matters. At 1 request a second the seam alone is about 7 minutes. Responses are kept with their URL, status and fetch time (in `history/raw_wiki` between runs, ADR-0020); an empty response is kept as the evidence that the gap is a source outage. The hour of 17 October 13:00 mixes dump and API buckets and says so (`source = mixed`). The upload refuses to run unless R2's live manifest starts exactly at `LIVE_START`, so the two series meet with no overlap and no hole (tested).

## 5. Reconciliation against `/1h`

### 5.1 The month checks (built)

For each dump month, two hours are checked against the Wiki's `/1h` (136 requests for 68 months). The hours are drawn from the month's hours whose 12 buckets are all in the dump, picked by the lowest SHA-256 of (source, month, file hash, hour): reproducible, as good as random, and unaffected by later fills. A check passes when:
- the item sets are equal,
- both volumes match exactly for every item, and
- every price is within the larger of 0.1% and the source's rounding: **0.02 GP** for decimal months, **1.01 GP** for months the dump stores as integers.

**Any failure quarantines the month:** it stays in the local lake with its evidence in `history/months.check_detail`, and `upload` keeps it out of R2.

**Evidence for the tolerance** (recorded responses, 14 to 19 October 2026, 27 hours with all 12 buckets, 87,631 item-hours):

| Check | Result |
|---|---|
| Item set, rolled-up 5m vs `/1h` | equal in 27 of 27 hours |
| High and low volumes | exact for 87,631 of 87,631 item-hours |
| Prices within 0.01 GP (full precision) | 146,493 of 146,493 priced item-sides; largest difference 0.005 GP |
| Prices within 0.1% alone | 146,292 of 146,493: **201 fail**, all cheap items where one rounding step exceeds 0.1% |
| Prices within 0.02 GP after rounding the hourly VWAP to 0.01 GP | all; largest difference 0.010 GP |

So A2's "VWAP within 0.1%" would fail on rounding alone. The plan reads it as "within the larger of 0.1% and the source's rounding" (Sylvester to confirm, section 9). Integer months are untested so far (the two months checked in the assessment matched exactly on volume); the bound is two whole-coin roundings plus one at 0.01 GP.

**First live check (22 October 2026, run 39709682542):** 65 of 68 months validated; volumes matched exactly in every checked hour, and the largest price difference was 0.5 GP in every month, as whole-coin 5-minute averages against `/1h`'s finer ones would give. Three months were quarantined:
- **2026-09 and 2026-10**, the dump's two months stored as floating point, failed only on prices of cheap items, by up to 0.5 GP, against the 0.02 GP decimal tolerance. The price type now comes from the values: a floating-point month whose prices are all whole coins takes the whole-coin tolerance (`history.price_type`).
- **2026-01** failed on the item set: in the hour of 3 January 18:00, the dump holds items (153, 1089, 1241, 2474, 3474 and possibly more) that `/1h` does not; volumes and prices matched. Sylvester chose the repair below (23 October 2026, on the agent's recommendation): `history.REPAIR_FROM_1H`. **Result** (run 39997838949, 742 requests): of 744 hours, 738 matched `/1h` and kept the dump's rows; six consecutive hours, 3 January 15:00 to 20:00 UTC, disagreed and took `/1h`'s rows; `/1h` answered every hour. The month is validated.

**If a month is quarantined:** stop and look. Fallback for an hourly-only month (built for 2026-01): list it in `history.REPAIR_FROM_1H`. `check-1h` then fetches every hour of the month from `/1h` (720 to 744 requests, about 12 minutes), and `build` compares each hour with the dump's rollup: an hour that agrees keeps the dump's rows, an hour that disagrees takes `/1h`'s rows (`source = wiki_api`), the independent reference (ADR-0005), and an hour `/1h` answers empty keeps the dump's rows. The month is then validated; its `check_hours` list every hour and its `check_detail` every replaced or empty hour, and the build report's `repaired` block counts them. The dump's extra items in a replaced hour are dropped with it: the reference wins a disagreement. A month inside the 5-minute window would also need its `/5m` buckets (about 8,900 requests, about 2.5 hours); not built.

### 5.2 The live reconciliation task (planned)

ADR-0005 makes `/1h` an independent check on the live 5-minute series. Plan: an hourly task `reconcile_1h` fetches `/1h` for the newest closed hour (1 request an hour; steady state goes from 14 to 15 an hour), compares it with the rollup of `silver/prices_5m` using the same rule, and records the result in `ops/`. That covers A2 for every live hour, and supplies the reconciliation input the Data grade is still missing (`docs/methodology/data_grade.md`, a later data-grade version).

## 6. Upload to R2

`ge-intel history upload` copies validated months: one commit per month for `history/prices_1h`, one per month for `history/prices_5m`, then `history/buckets_5m` and `history/months`, so a reader never sees a month before its rows. Before writing it:
- runs the cost guard's month-to-date check (fails closed; needs the analytics token in the shell);
- refuses if current storage plus the upload would pass **5 GB** (A5);
- refuses if the live manifest in R2 does not start at `LIVE_START`.

Cost: about 74 commits, about 740 Class A and 3,700 Class B operations (spike S1's per-commit figures), 0.07% and 0.04% of the monthly free allowance. A repeat upload writes only what changed: a month whose row in R2's `history/months` equals the local one is already there and is skipped, and with nothing new it commits nothing (tested). Nothing vacuums `history/`, so rewriting an unchanged month would leave its old files in R2 for good. An upload holds back quarantined months; a later one adds each month once it is validated.

### 7.4 Revision audit (D8)

- Live: an hourly task re-fetches one bucket from 1 hour, 24 hours and 7 days ago (3 requests an hour), compares the body hash with the manifest's `raw_sha256`, and on a difference compares the parsed rows (a reordered body is not a revision). - History: the month checks are a revision check at one to five years; two different stored bodies for one bucket stop the build.
- If revisions appear, a bounded re-fetch window follows (ADR-0005).

Exit code 4 means a step's inputs are not ready (for example, the dump is not fully downloaded); the log says which.

## 10. Risks

| Risk | Mitigation |
|---|---|
| A month fails its check | quarantined, kept out of R2, fallback decided case by case (5.1) |
| The dump's gaps are many more than the assessment's sample suggests | **Happened:** 2,986 gaps (first build, 21 October). The fill paces itself at 1 a second (about 57 minutes) and `limit` splits it; empty answers are kept as confirmed outages for A1 |
| Kaggle serves a different file under version 1 | size and hash pins refuse it |
| Kaggle refuses a runner without a login (not verifiable from the agent's session) | the download step fails with the HTTP status; add a Kaggle API token as repository secrets and basic authentication in `kaggle.download` (ADR-0020) |
| A long live outage | the gap-fill window bounds automatic catch-up; older gaps go through the runbook |
| R2 storage | the upload refuses past 5 GB; ADR-0019 retention on since 24 October (section 8) |
| Historical buy limits unknown | unchanged from the discovery report: current limits, flagged |
